Native weapon gameplay composition

src/weapon_runtime.c binds the recovered weapon controller, animation state, selection and switching to native map/entity aiming, hitscan geometry and combat. An actual shot from weapons 1 through 5 can now change a registered script actor's health, award a kill, and feed its existing enemy death/group/corpse handling. This document describes the weapon library integration; the current playable frontend also supplies rendering, audio and PC input. See native-game.md for admitted campaign coverage and limits.

Automatic cadence in the PC port

The frontend now enables finish_fire_before_switch: a requested weapon change cannot lower the current weapon until its firing/reload sequence completes. Continuous weapons stop issuing attacks while their current animation cycle finishes, then use the original release/wind-down and handoff. A stale loop completion marker cannot bypass the wait. Selection changes can replace the queued destination; selecting the current firing weapon cancels the handoff. Pause freezes the wait. This option defaults off for recovery comparisons. Q is a frontend last-used request; history records actual weapon commits and survives campaign carry, rather than recording every intermediate request.

Short PC fire clicks

The frontend enables buffer_fire. The input sampler already retains a mouse down/up pair between polls, but that one-tick pulse could end before the weapon started firing. The runtime now records one pending attack for the requested weapon. It keeps fire held through startup, raising, cooldown and reload until the controller increments that weapon's actual shot counter. That clears the pending attack; the next released update stops continuous fire. Starting an animation alone does not consume the click. Holding the button continues normally with the measured automatic cadence, without an accelerated initial shot.

This is one outstanding attack, not a queue of every click during a reload. Focus loss, disabled controls, pause, death, respawn, input state3, empty ammo or a different requested weapon cancel it. A physical release still acknowledges the original held-fire protection gate while the pending attack is retained. The option defaults off in the library; canonical ROM controllers are unchanged.

Ownership and frame ordering

Current special-weapon integration also binds weapon8's native combat explosion, weapon9's shared-pool E3 allocation/animation/insertion, and both palette requests. See special-weapons.md. The standalone legacy fixture below deliberately leaves optional projectile services unbound; its unsupported cases describe that fixture, not the current playable frontend.

Initialize SsaWeaponRuntime at a stable address after player gameplay and combat bindings exist. Current/requested weapon must already be valid; init does not invent a loadout. The player must be one of combat's indexed runtimes. The initial weapon-view fields provide position, sprite type, layer and owner; the owner is the original player index plus one. The runtime owns dedicated aim/hit and interaction scratch and does not borrow movement or camera scratch. Free it before gameplay, combat and world teardown.

ssa_weapon_runtime_step composes the F150 wrapper gates and original 122AC sequence: cooldowns, 12230 near-wall lowering, selection 11604, controller 116E4, and lower/commit/raise 12160. Supply the original held/pressed button masks separately from movement flags. Fire is bit 1. The GAME projections, including local display/motion player indices, remain explicit inputs.

Original main 0244C updates entities, sector movers and scripts before sprite controllers F85C; the weapon object reaches F150 and 122AC there. E460 animation advancement follows all sprite controllers. Keep animation separate and tick each object once after gameplay/VM work: controller decisions consume the previous tick's completion state. See weapon-animation.md and weapon-controller.md for recovered timing and state behavior.

Pause flag 1 skips the wrapper, including its visibility update. Input state 3 skips the weapon controller but still refreshes object flag 1 from the display local player's movement flag 8. Object ownership and all required callbacks are validated before either skip. Native errors preserve prior effects; they are not transactions.

Tracing and combat

Aiming and hitscan share their dedicated trace state, retaining opening and slope globals in the original order. The controller's temporary aim marker is cleared before attack events. The hit query uses the body's original facing byte, as recovered from A444, while autoaim uses the controller heading. The adapter consumes HITSCAN and EXPLOSION internally. Wall hits call impact with a NULL target. For entity hits, zero damage or zero health suppress impact; otherwise impact precedes damage. Failure there leaves the target unharmed.

A synchronous combat scope locks combat, script spawning and every bound player through callbacks. Nested weapon/gameplay/runtime teardown is rejected. Callback implementations must not mutate map layout or directly remove registered bodies. Ordinary world tracing obtains and releases its own query lock before damage.

Damage source remains the firing body after a step. Credit player and selected shot-hit pointer clear on exit, including failure. The selected hit counter is indexed by the weapon current before selection. Multiplayer callers must bind credited_kills to that shooter's persistent kill byte. The shared combat kill pointer is borrowed during firing and restored afterward; two shooters must not share an accidental scratch counter.

The gameplay WEAPON_ANIMATION respawn callback can call ssa_weapon_runtime_respawn. This helper is allowed while player gameplay owns its update lock, copies the recovered view fields, and sets animation/period and weapon action. It is prohibited during a weapon update. This preserves the existing native jump settings and H camera mode across actual respawn.

Presentation events remain mandatory external callbacks. Unsupported projectile or effect allocation requests must fail explicitly. This adapter does not supply a silent no-op projectile implementation. Weapons 6, 7 and 10 reach their real creation boundary but have no native projectile runtime here; advanced effect and request consumers likewise remain outside this module.

Native integration validation

Scripted CD fixtures use a private in-memory ROM copy; the original file is unchanged. The test-only original-ROM CPU is not linked or used.
