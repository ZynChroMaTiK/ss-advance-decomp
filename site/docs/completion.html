Project reference snapshot. Recovery notes retain earlier subsystem milestones; use the current feature overview for playable scope.

Original timed completion tally and record pipeline

The native backend now recovers the single-player tally loop inside original 08002564, followed by the completion data sequence at 08002B20: 1231C weapon capture, 1E48 totals accumulation, 1CF4 checkpoint capture, then increment the level. These are available through completion.c and native_completion.c. The Windows frontend now runs this tally and commits its bonus-adjusted record before advancement, chapter panels or the ending.

Playable pause and completion screens

Esc/P opens Continue/Quit over a frozen level. Quit opens the original localized Yes/No notice with No selected, then returns to Main. Application exit is the separate bottom-row Quit on Main. Arrows/WASD, Enter/Space and mouse hover/click select; Esc cancels the confirmation or resumes from the root. The pause adapter in pause.c binds the existing recovered mode_control.c/021E4 with one player, queues its actual commands/notices and retains their prefix state changes. It is not another replacement controller. Network pause flags are outside this single-player presentation owner.

intermission.c owns a separate84-slot sprite pool/cache/OAM, borrows frozen game assets/math, and renders the original E914/E9D4 localized notice glyphs, ECF8 score digits and EE60-compatible bonus spacing. Pending digits use Y88/120; score remains at Y8. It uses the original30-entry text blend table. The PC layer darkens the captured world over30ticks and marks the selected pause row white; those composition choices are host adaptations, not pixel-equivalence claims. Draws never tick gameplay or the tally. The high-resolution software scene is retained; GBA remains240x160. Private OAM copies remove old notices from pause's backdrop and remove all old HUD sprites from completion's backdrop.

Completion starts automatically from the living native input-state3 boundary. The host calls the original tally once per60Hz presentation tick. Held mouse fire/Enter/Space accelerates counting. A fresh click/Enter/Space settles the current time/ammo bonus in full, including during its initial hold. This PC policy lives in intermission.c; the recovered completion.c remains unchanged. The final message stays for180 fully visible ticks (three seconds); a separate fresh confirm after60 visible ticks can shorten that reading hold. Glyph loading does not consume the window. Both paths still wait for the actual music player to finish, including muted playback; missing audio is the explicit silent path. Tally command16 plays the existing count cue. Music9 is confined to completion. The original wrapped negative par difference can exist briefly at stage3; the native display hides it instead of overflowing the original8-digit scratch.

After the music/reading hold finishes, the frontend calls ssa_native_completion_record once, stores totals/checkpoint rows for the campaign session, and puts the final score into the next-level carry/entry snapshot. Reload does not accumulate the same counters again. Password/standalone setting-byte policy reaches record capture; carried campaign starts use setting0. Ammo is retained. Chapter6 and ending12 routes run after recording; R on the next map restores that bonus score. Existing progress unlock/save behavior remains separate. High-score lists and name entry are still pending, and campaign-session totals are not a new disk-save format.

Audio commands4/5 now suspend/resume existing native music/effect instances and their envelope/sample/sequence clocks. New menu cues remain independent; quit's command6 retires the old instances. Synth controls mute the paused music tracks and restore them on resume. Suspension is immediate in the PC mixer; the original temporary audio fade envelope and physical MIDI-device timing are not claimed identical by this change.

Bonus and timing behavior

The original loop increments GAME+00 once per presentation tick while gameplay elapsed time stays frozen. It reads the twelve original par times at 0844A610: 120, 300, 300, 420, 360, 360, 300, 360, 360, 360, 360, 360 seconds.

Phase Original behavior
Time bonus Positive par - elapsed/60 becomes 1000 * (difficulty+1) points per remaining second
Time counting Wait 60 ticks, then transfer 100 points per tick, or 1000 while fire is held
Ammo bonus Sum signed ammunition for weapons3..10; positive first scaling becomes 100 * sum * (difficulty+1)^2
Ammo counting Wait 60 ticks, then use the same 100/1000-point transfer
Short wait 30 ticks after ammo counting; held fire can skip it
Final message Submit original localized text ID B9+level and sound7, then wait for music-player completion

All arithmetic uses the original wrapped 32-bit values and signed branch decisions. The ammo positivity test occurs after the first multiplication by 10*(difficulty+1), before the second; do not replace it with a saturating formula. Ammo is not consumed. Weapons1 and2 never contribute. Score wraps.

Normal time completion goes directly to ammo setup. The original stage2 short wait exists in the jump table but is not entered by the ordinary recovered path; the native controller preserves and tests it. Counting emits original command16 only on frame-counter multiples of8 and only for nonfinal transfers. The final message cannot dismiss on its first submission tick. Thereafter a fresh fire press can bypass the remaining 60-tick hold, but music must be finished. Without a fresh press, it waits for that hold to reach zero too. Held fire and pressed fire are separate inputs.

All twelve levels use that same cue; localized text IDsB9..C4 provide the different Sam lines. There is no per-line speech lookup here.

Player0 owns music, including completion command9 (Egypt song78/Rome7F). The old host incorrectly checked effect instances of song7. screen_completion_music_finished now reads player0 under the mixer lock. The native tests render both real completion tunes and the cue, confirming that music continues after the cue ends and the cue uses no PCM speech sample. Completion music still starts at tally entry, not at the final line, and is not restarted there.

Original message IDs are B6 (time), B7 (time zero/ammo), B8 (both zero), and B9..C4 for the twelve final Sam messages. Native composition

ssa_native_completion_init requires an idle, completed, living game in original input mode3. It copies the current score, frame counter, elapsed time, ammunition and difficulty into the tally. The source game remains frozen and unchanged. Call ssa_completion_step at the original 60Hz presentation cadence, with explicit held/pressed input and original voice-finished status. Device or render rate must not alter the tally's timing.

After the tally finishes, ssa_native_completion_record builds a value-only SsaCompletionRecord from caller-owned prior totals. It captures actual equipped and requested weapons separately, ownership and ammunition; refreshes weapon statistics with the original setting byte; accumulates the bonus-adjusted score and level counters; saves the checkpoint rows; and supplies next-level index. Setting0 retains weapon shots/hits; any nonzero byte clears both before accumulation and checkpoint capture.

First success marks the tally recorded; duplicate and premature attempts fail before output changes. It rejects busy/error/source changes, including score, counter, elapsed, bonus ammunition and completion state. Null failures preserve output and the recorded flag. Canonical inventory health/protection supplies the native projection of original body/player vitality. Source game and prior totals remain unchanged, including source weapon counters. The resulting record is safe to retain after game teardown; it contains no borrowed pointers.

This remains an explicit composition API. It does not itself update SsaNativeCarry, mutate the live game score, write save.dat, grant equipment, unlock/admit levels, run next-level player construction, or route chapters/endings. All twelve maps are now admitted at the user's request for manual validation. The active E914/E9D4 service supplies gameplay's original localized pickup/boss/death messages; see hud-notices.md. The original pre-tally world capture, tally-specific notice calls, on-screen bonus digits and final audio dismissal are now connected by the host described above. That host replaces the old direct Enter transition with the timed sequence; it never commits the earlier pre-bonus score or instantly awards the bonus instead of counting.
